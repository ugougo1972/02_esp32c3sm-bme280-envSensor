# 04_ctx

## 目的

本ファイルは、携帯型環境センサーロガー初号機における `context_code` の定義と運用ルールを整理するためのものである。  
`context_code` は、環境データ単体では分からない利用者の状況を補助的に記録するために用いる。

初号機では、まず **少数の固定コードで安定して記録できること** を優先し、入力UIの複雑化は避ける。

## 基本方針

- `context_code` は **CSVの1列として保存**する
- 初号機では、**固定コード選択式**を採用する
- コード数は必要最小限にとどめる
- 意味が曖昧なコードは増やさない
- まずは **手動入力** を前提とする
- センサ推定による自動判定は初号機では行わない
- 未入力時の既定値を明確にする

## context_code の役割

`context_code` は、以下のような環境条件の補足に使用する。

- 屋内 / 屋外
- 移動中かどうか
- 自宅 / 職場などの代表的な滞在場所
- 解析時に分類軸として使いたい行動状態

これにより、同じ気圧・温湿度・照度・UVでも、状況別にログを見分けやすくする。

## 初号機のコード定義

| code | 状態名 | 意味 | 使用方針 |
|------|--------|------|----------|
| 0 | unknown | 不明 / 未入力 / 未設定 | 既定値 |
| 1 | indoor | 屋内 | 一般的な屋内滞在 |
| 2 | outdoor | 屋外 | 一般的な屋外滞在 |
| 3 | moving | 移動 | 乗り物移動、徒歩移動など |
| 4 | office | 職場 | 主な勤務場所 |
| 5 | home | 自宅 | 主な居住場所 |

## 既定値

### 基本ルール

- `context_code` の既定値は **0（unknown）**
- 起動直後に明示的な操作がなければ `0` を使用する
- UI未実装段階、または入力忘れの場合も `0` を許容する

### 理由

- 推測値を勝手に入れないため
- ログの意味を曖昧にしないため
- 後処理で「不明」として除外・分類しやすくするため

## CSV上の扱い

`context_code` は、CSV上では数値コードとして保存する。

### 保存例

```text
timestamp,temp_c,hum_pct,press_hpa,als,uvs,context_code
2026-04-05 15:11:11,22.52,62.38,1006.26,565,0,1
2026-04-05 15:12:11,22.54,62.28,1006.23,564,0,3
2026-04-05 15:13:11,22.55,62.17,1006.26,563,0,0
```

### 保存ルール

- 数値コードで保存する
- 日本語文字列はCSV本体には保存しない
- 解析時に別表で意味へ変換する

## UI入力方針

### 初号機の前提

- 入力UIは **Rotary Encoder** を前提とする
- 初号機では、`context_code` 専用の複雑な編集画面は未実装でもよい
- 少なくとも以下のいずれかで運用可能とする  
  - 固定値で暫定運用  
  - MENU配下で切替  
  - LOG前後に簡易選択

### 想定する入力方式候補

| 方式 | 内容 | 状況 |
|------|------|------|
| A | 起動時は前回値を引き継ぐ | 候補 |
| B | MENUから選択変更する | 候補 |
| C | LOG画面で変更する | 候補 |
| D | 常に `0` 固定で運用する | 暫定運用可 |

## 前回値引き継ぎの扱い

### 方針

- 初号機では **前回値引き継ぎは未確定**
- 実装する場合でも、誤った状態が長時間継続しないよう注意する
- 自動引き継ぎが不安な場合は、常に `0` 開始でよい

### 判断基準

| 方針 | 長所 | 短所 |
|------|------|------|
| 常に `0` 開始 | 誤記録を避けやすい | 入力手間が増える |
| 前回値引き継ぎ | 手間が減る | 状況変化に追従しない可能性 |

初号機では、**まず記録成立を優先**し、必要なら後段で前回値引き継ぎを追加する。

## 状態定義の運用ルール

### 1. unknown（0）

以下の場合は `0` を使用する。

- 入力していない
- 状況が混在して判断不能
- 一時的にどれを選ぶべきか不明
- UI未実装段階

### 2. indoor（1）

以下を目安に使用する。

- 一般的な建物内
- 商業施設内
- 病院内
- 公共施設内
- 自宅 / 職場以外の屋内

### 3. outdoor（2）

以下を目安に使用する。

- 屋外滞在
- 徒歩中で「移動」より屋外環境記録を重視したい場合
- 公園、道路、屋外広場等

### 4. moving（3）

以下を目安に使用する。

- 徒歩移動
- 車移動
- 電車 / バス移動
- 環境変化が連続して大きく変わる移動中

### 5. office（4）

以下を目安に使用する。

- 主たる勤務先
- 日常的に長時間滞在する職場
- 解析上、一般屋内と分けたい勤務環境

### 6. home（5）

以下を目安に使用する。

- 自宅滞在
- 解析上、一般屋内と分けたい生活空間

## 選択優先ルール

状態が重複する場合は、以下の優先で選択する。

| 優先度 | 状態 | 例 |
|--------|------|----|
| 1 | moving | 電車移動中、徒歩移動中 |
| 2 | office | 職場建物内 |
| 3 | home | 自宅内 |
| 4 | outdoor | 屋外滞在 |
| 5 | indoor | その他一般屋内 |
| 6 | unknown | 判定不能 |

### 解釈例

| 状況 | 推奨コード | 理由 |
|------|------------|------|
| 職場で席に着いている | 4 | office を優先 |
| 自宅で過ごしている | 5 | home を優先 |
| バス移動中 | 3 | moving を優先 |
| 屋外を歩いている | 3 または 2 | 移動重視なら 3、屋外環境重視なら 2 |
| 商業施設内 | 1 | 一般屋内 |
| 判断できない | 0 | unknown |

## 解析時の扱い

### 基本方針

- `context_code` は補助情報として扱う
- 欠損や `0` があってもログ全体を無効化しない
- 集計時にコード別で分けて比較できるようにする

### 解析例

- `home` と `office` で気圧・温湿度差を見る
- `moving` 時の環境変化幅を見る
- `unknown` を除外して集計する
- `indoor` / `outdoor` で照度・UV差を見る

## 実装上の注意

### 1. 推測しない

- ソフト側で勝手に `indoor` / `outdoor` を判定しない
- LTR390 や BME280 の値だけで context を自動決定しない

### 2. コード追加を急がない

- 初号機では 0〜5 の範囲で固定する
- `hospital`, `shopping`, `commute` などの細分化は後段で検討する

### 3. ログとの整合を保つ

- `03_LOG_FORMAT.md` の `context` / `context_code` 列と意味を一致させる
- 実装コード側の定数名も本定義と一致させる
